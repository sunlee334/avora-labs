# 토스페이먼츠 연동

**주문서형 결제위젯** 으로 연동합니다. 테스트 키가 들어와 있어 지금 동작을
확인할 수 있고, 라이브는 계약·심사 뒤입니다.

이 문서는 계약이 끝난 뒤 무엇을 어떤 순서로 하는지 적습니다. 여기에 실제 키나
상점 정보를 적지 마세요 — 이 파일은 저장소에 커밋됩니다.

출처: [환경 설정](https://docs.tosspayments.com/guides/v2/get-started/environment) ·
[배포 체크리스트](https://docs.tosspayments.com/guides/v2/deploy-checklist) ·

## 지금 어디까지 되어 있나

| 조각 | 자리 | 상태 |
|---|---|---|
| 결제위젯(주문서형) | `src/lib/toss.ts` · `src/pages/[lang]/checkout.astro` | 됨 |
| 승인 요청 | `worker/payments/tosspayments.ts` | 됨 |
| 승인 라우트 | `worker/index.ts` → `/api/payments/confirm` | 됨 |
| 금액 위변조 방어 | 승인 전에 D1 의 주문 금액과 대조 | 됨 |
| 실패 분류 | 에러 코드별 재시도 판정 | 됨 |
| 완료·실패 화면 | `src/pages/[lang]/order/complete.astro` | 됨 |
| **클라이언트 키** | `src/config/payment-config.json` → `countries.KR.provider.clientKey` | **테스트 키 있음** |
| **시크릿 키** | 워커 시크릿 `TOSS_SECRET_KEY` | **없음** |
| **PG 선택** | 워커 변수 `PAYMENT_PROVIDER` | **없음** |

`clientKey` 가 비어 있으면 체크아웃은 위젯 없이 주문만 만들고 완료 화면으로
넘어갑니다. **일부러 남겨 둔 갈래입니다** — 키가 없는 환경에서도 주문 생성부터
완료 화면까지를 통째로 돌려볼 수 있어야 합니다.

**왜 결제창이 아니라 주문서형인가.** 처음에는 `payment()` 로 결제창을 띄웠는데,
그 API 의 문서 제목이 **"결제창(구버전)"** 이고 `customerKey: ANONYMOUS` 는
`widgets()` 쪽에만 문서화돼 있었습니다. 근거 없는 사용이었습니다.

## 아직 없는 것 — 결제를 열기 **전에** 채워야 합니다

### 결제 취소·환불 경로가 통째로 없습니다 ★

`OrderStatus` 에 `'cancelled'` 가 있지만(`worker/orders.ts:14`) **아무도 그 값을
설정하지 않습니다.** 취소 라우트도, 관리 화면의 취소 동작도, 어댑터의 취소
메서드도 없습니다. `PaymentAdapter` 인터페이스에는 `confirm()` 하나뿐입니다.

두 가지 이유로 결제를 열기 전에 필요합니다.

- **법.** 「전자상거래법」 제17조의 청약철회는 7일입니다. 받을 방법이 없으면
  안 됩니다.
- **토스 배포 체크리스트**가 "결제 취소 및 부분 취소 기능 테스트" 를 라이브
  전환 항목으로 요구합니다.

지금 만들지 않은 이유: 부르는 곳이 없는 인터페이스를 먼저 만들면 그 모양이
실제로 필요한 것과 어긋납니다. 관리 화면에서 취소를 어떻게 다룰지(전액만인지
부분 취소도인지, 누가 누를 수 있는지)를 정한 뒤에 붙이는 편이 낫습니다.

승인 API 와 같은 자리에 `POST /v1/payments/{paymentKey}/cancel` 이 있고,
멱등키를 함께 보내야 중복 취소가 나지 않습니다.

**자동 정리와 헷갈리지 마세요.** 주간 크론이 하루 지난 `pending` 을 `failed`
로 옮깁니다(`worker/digest.ts` 의 `sweepAbandoned`) — 그건 **버려진 결제
시도** 를 치우는 것이지 환불이 아닙니다. `cancelled` 상태는 사람이 취소한
것을 위해 비워 두었습니다.

### 가상계좌 — 켜기 전에 셋을 보세요

`payment-config.json` 에서 `vbank` 가 꺼져 있어 지금은 필요 없습니다. 다만
**그 파일이 보증해 주지 않습니다** — 실제 노출은 개발자센터가 정합니다.
켤 때 함께 봐야 하는 것이 셋입니다.

1. **웹훅을 먼저 등록합니다.** 입금 통지를 못 받으면 주문이 영원히 `pending`
   입니다.
2. **주간 정리가 입금 대기 주문을 죽입니다.** `sweepAbandoned`(`worker/digest.ts`)
   는 하루 지난 `pending` 을 `failed` 로 옮깁니다. 가상계좌는 며칠을 기다리므로,
   `payment_key IS NULL` 조건만으로는 부족합니다 — 상태를 따로 가르거나 기한을
   늘려야 합니다.
3. **승인 응답이 `WAITING_FOR_DEPOSIT` 으로 200 을 돌려줍니다.** 어댑터가
   `DONE` 이 아니면 성공으로 보지 않도록 막아 두었지만(`PAYMENT_NOT_DONE`),
   그때 주문을 어떤 상태로 둘지는 정해야 합니다 — 지금은 `pending` 으로
   열어 두고 사람을 부릅니다.

## 막혀 있는 것

1. **토스페이먼츠 상점 개설·계약.** 키는 그 뒤에 발급됩니다.
2. **결제수단 심사.** 카드사 심사는 상점 개설과 별개로 시간이 걸립니다.
3. **판매 방식 결정.** `payment-config.json` 의 `KR.checkout` 이 지금 `"external"`
   입니다. 자사 결제로 열려면 `"internal"` 로 바꾸고 `src/data/product.json` 의
   `price` 를 채워야 합니다(`SELLS_DIRECTLY` 가 둘을 함께 봅니다).

## 테스트 환경에서 먼저 돌리기

계약이 끝나 **테스트 키**가 나오면 라이브 없이 여기까지 확인할 수 있습니다.

**순서가 중요합니다 — 시크릿이 먼저입니다.** `clientKey` 는 빌드 상수라 넣고
배포하는 순간 결제 화면이 열립니다. 그때 워커에 시크릿이 없으면 승인 라우트가
503 을 돌려주고, **손님은 결제를 마친 뒤 실패 화면을 봅니다.** 반대 순서에는
부작용이 없습니다 — 시크릿만 있고 위젯이 없으면 보낼 결제가 없습니다.

1. 워커 쪽 두 값을 먼저 넣습니다. **`wrangler.jsonc` 맨 아래에 같은 내용이 적혀
   있습니다** — 그쪽이 정본이고 여기는 순서를 보여주는 것뿐입니다.

   ```
   npx wrangler secret put TOSS_SECRET_KEY       # test_gsk_… — 시크릿
   ```

   `PAYMENT_PROVIDER` 는 시크릿이 아닙니다. 값이 `"tosspayments"` 라는 문자열
   하나이고 숨길 것이 없으므로 `wrangler.jsonc` 의 `vars` 에 넣습니다 — 무엇이
   켜져 있는지가 저장소에 남아야 합니다. `GOOGLE_CLIENT_ID`·`KAKAO_REST_API_KEY`
   와 같은 취급입니다.

   ```jsonc
   "vars": { "PAYMENT_PROVIDER": "tosspayments" }
   ```

   `PAYMENT_PROVIDER` 가 없으면 승인 라우트가 503 `PAYMENT_NOT_CONFIGURED` 를
   돌려줍니다. 일부러 그렇게 해 둔 것입니다 — 설정이 반쯤 된 채로 결제가 열리는
   것보다 낫습니다.
2. `payment-config.json` 의 `countries.KR.provider.clientKey` 에 `test_gck_…` 를
   넣습니다. 공개돼도 되는 값이라 커밋합니다 — 무엇이 켜져 있는지가 코드에
   남는 편이 낫습니다. **주문서형 키는 `gck`/`gsk` 입니다**(API 개별 연동의
   `ck`/`sk` 와 다릅니다).
3. 개발자센터 **테스트 결제내역**에서 승인·취소를 확인합니다.
4. 에러 경로는 `TossPayments-Test-Code` 헤더로 재현할 수 있습니다(문서 참고).

테스트 환경에서는 실제 카드번호를 넣어도 돈이 빠지지 않습니다. 가상계좌 번호에는
앞에 `X` 가 붙고 실제 입금은 안 됩니다. API 는 분당 100건으로 제한됩니다.

**순서를 지키세요.** 키만 바꾸고 나머지를 빼먹으면 결제는 열리는데 실패가 조용히

- [ ] API 버전이 최신(`2022-11-16`)인지 확인한다 — 키에 묶인 값이라 개발자센터에서 본다

- [ ] 실제 카드로 소액 결제 → **취소**까지 한 번 돌린다

- [ ] 테스트 결제 데이터를 운영 D1 에서 정리한다

## 두 가지 함정

### 시크릿 키는 저장소에 두지 않는다

배포 체크리스트가 못 박은 문장입니다 — "시크릿 키는 공개적으로 접근할 수 있거나
버전 관리 시스템으로 접근할 수 있는 코드에 포함되면 안 돼요."

두 키는 생김새가 비슷해서 붙여넣기 한 번으로 섞입니다.

| 키 | 접두어 | 어디에 |
|---|---|---|
| 클라이언트 | `test_gck_` · `live_gck_` | 브라우저에 그대로 나갑니다. 설정 파일에 커밋 |
| 시크릿 | `test_gsk_` · `live_gsk_` | 워커 시크릿에만. **한 번 새면 재발급** |

주문서형은 `g` 가 붙습니다(`gck`/`gsk`). API 개별 연동(브랜드페이·자동결제)은
`ck`/`sk` 입니다. 검사는 둘 다 잡습니다 — 처음에는 `_sk_` 만 봐서 **주문서형
시크릿이 그대로 지나갔습니다.**

빌드도 막습니다. `PUBLIC_TOSS_CLIENT_KEY` 에 시크릿을 넣으면 `runtime.ts` 가
빌드를 세웁니다 — 저장소 스캔은 `dist` 를 건너뛰므로 그 경로만 뚫려 있었습니다.

`tests/e2e/payment-secrets.spec.ts` 가 저장소 전체를 훑어 `_sk_` 형태를 막습니다.
그 검사가 빨개지면 파일에서 지우는 것으로 끝내지 말고 **개발자센터에서 키를
재발급**하세요 — 이미 커밋됐다면 히스토리에 남아 있습니다.

### 승인 실패를 함부로 확정 짓지 않는다

`worker/payments/tosspayments.ts` 의 `isRetriable()` 이 하는 일입니다.

`ALREADY_PROCESSED_PAYMENT` 는 실패가 아니라 **이미 승인이 끝났다**는 뜻입니다.
`PROVIDER_ERROR` 같은 일시적 오류는 HTTP 4xx 로 옵니다. 이것들을 확정 거절로
읽으면 주문이 `failed` 로 닫히는데, 그 순간 **돈은 나갔고 장부에는 실패로
남습니다.**

`ALREADY_PROCESSED_PAYMENT` 를 만나면 **그 자리에서 조회로 확정합니다** —
`GET /v1/payments/orders/{orderId}` 로 실제 상태를 보고, `DONE` 이면서 금액이
맞으면 승인 성공으로 돌려줍니다. 처음에는 `pending` 으로 두고 "대사에 맡긴다"
고 적었는데, 검토에서 **그 대사가 저장소 어디에도 없다** 는 것이 드러났습니다.
조회가 실패하면 그때 `pending` 으로 떨어집니다 — 최악을 피하는 바닥은 그대로입니다.

승인 실패는 Sentry 로 갑니다(`area: payment-confirm`). 전에는 이 핸들러가
실패를 던지지 않고 JSON 으로 돌려줘서 **한 건도 올라가지 않았습니다.**

분류를 고칠 때는 `tests/e2e/commerce/toss-adapter.spec.ts` 를 함께 보세요.
